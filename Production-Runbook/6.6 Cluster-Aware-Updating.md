# 6.6 Cluster-Aware Updating (CAU) for HVCL01

> After 6.5, **before any customer**.
> Goal: patch HV01–HV04 one node at a time with **no VM downtime**. The first run doubles as a full drain / live-migration / failback test of the cluster while only management VMs exist.
> Chosen host-patching method: **CAU**. Don't also use VMM's WSUS compliance/remediation for these hosts: pick one method.

## 1. What CAU does

For each node, one at a time:

| Step | Action |
|---|---|
| 1 | **Pause + drain** the node: clustered VMs are live-migrated to the other nodes |
| 2 | **Install updates** (Windows Update plugin: from WSUS or Microsoft Update, per the `SRV - Update Source` GPO) |
| 3 | **Reboot** if needed |
| 4 | **Resume + failback**: VMs move back to their preferred node |
| 5 | Next node |

With `-MaxFailedNodes 0`, CAU **stops** at the first node that fails, so a broken update never reaches the whole cluster.

## 2. Domain controllers: expected behaviour

DC01 (on HV01) and DC02 (on HV02) are **not clustered** (local disk, 2.1 / 4.1). CAU can't live-migrate them:
- When CAU drains **HV01**, DC01 **shuts down with the host** (automatic stop action: ShutDown) and **starts again after the reboot** (automatic start action: Start). During that time **DC02 serves the domain**.
- The same happens to DC02 when HV02 is updated, with DC01 serving.
- CAU updates **one node at a time**, so **both DCs are never down together**.

This is expected. A short "DC01 not reachable" alert during the HV01 step isn't a failure.

## 3. Prerequisites

| # | Prerequisite | How to check / where it's done |
|---|---|---|
| 1 | Cluster healthy | Gate 5.2: 4 nodes Up, CSV Online |
| 2 | Update source working | 2.1 §7: `SRV - Update Source` GPO (WSUS or WinHTTP proxy) applied on the hosts (`gpresult /r` on a host) |
| 3 | **No automatic installs/reboots on the nodes** | The same GPO sets `NoAutoUpdate = 0` and `AUOptions = 2` in **both** cases (WSUS and proxy, 2.1 §7). Check on a host (HV0x): `Get-ItemProperty HKLM:\Software\Policies\Microsoft\Windows\WindowsUpdate\AU \| Select-Object NoAutoUpdate, AUOptions` → `NoAutoUpdate = 0`, `AUOptions = 2` |
| 4 | Capacity for N-1 | `ClusterReserve 1` (6.3). All infra VMs fit on 3 nodes |
| 5 | AD: CAU computer object | The CNO `HVCL01$` can create computer objects in `OU=Clusters`, **or** pre-stage `HVCL01-CAU` there and give `HVCL01$` Full Control on it (needed for Phase B) |
| 6 | Firewall | Opened by CAU itself with `-EnableFirewallRules` ("Remote Shutdown" rule group on the nodes) |
| 7 | CAU tools on MGMT01 | `Install-WindowsFeature RSAT-Clustering -IncludeAllSubFeature` (CAU GUI + `ClusterAwareUpdating` PowerShell module) |
| 8 | Maintenance window | Agreed with Etisalat (0.2 §1 #25) |

Optional pre-stage of the CAU object (prerequisite #5):

```powershell
# DC01 (or MGMT01 with RSAT-AD-Tools)
$ou = "OU=Clusters,OU=Infrastructure,DC=etisalat,DC=local"
New-ADComputer -Name "HVCL01-CAU" -Path $ou -Enabled $false -Description "CAU clustered role for HVCL01"
$cno = Get-ADComputer "HVCL01"
$acl = Get-Acl "AD:CN=HVCL01-CAU,$ou"
$acl.AddAccessRule((New-Object System.DirectoryServices.ActiveDirectoryAccessRule($cno.SID, "GenericAll", "Allow")))
Set-Acl "AD:CN=HVCL01-CAU,$ou" $acl
```

## 4. Phase A – remote-updating (first months)

MGMT01 is the update coordinator. The operator starts each run in the maintenance window.

```powershell
# MGMT01
Install-WindowsFeature RSAT-Clustering -IncludeAllSubFeature
Import-Module ClusterAwareUpdating

# 1. Readiness check (all tests must pass, except the self-updating ones until Phase B)
Test-CauSetup -ClusterName HVCL01

# 2. Preview: which updates each node would get
Invoke-CauScan -ClusterName HVCL01 -CauPluginName Microsoft.WindowsUpdatePlugin | Format-Table NodeName, UpdateTitle

# 3. The run
Invoke-CauRun -ClusterName HVCL01 -CauPluginName Microsoft.WindowsUpdatePlugin `
    -MaxFailedNodes 0 -MaxRetriesPerNode 2 -RequireAllNodesOnline -EnableFirewallRules -Force

# 4. Result
Get-CauReport -ClusterName HVCL01 -Last -Detailed
```

GUI alternative on MGMT01: the **Cluster-Aware Updating** app (Server Manager → Tools), or **Failover Cluster Manager → HVCL01 → More Actions → Cluster-Aware Updating** → Connect → *Preview updates for this cluster* → *Apply updates to this cluster*.

During the first run, watch from MGMT01:
- `Get-ClusterGroup | Format-Table Name, OwnerNode, State`: VMs move away from the node being updated and back.
- `ping -t DC01` / `ping -t DC02`: only one is down at a time (§2).

## 5. Phase B – self-updating (after 2–3 clean months)

The CAU clustered role runs the same procedure on a schedule, with no coordinator machine.

```powershell
# MGMT01
Add-CauClusterRole -ClusterName HVCL01 -VirtualComputerObjectName HVCL01-CAU `
    -CauPluginName Microsoft.WindowsUpdatePlugin `
    -DaysOfWeek Saturday -WeeksOfMonth 3 `
    -MaxFailedNodes 0 -MaxRetriesPerNode 2 -RequireAllNodesOnline -EnableFirewallRules -Force
# Schedule placeholder: 3rd Saturday of the month. Set it to the maintenance window agreed with Etisalat (0.2 §1 #25)

Get-CauClusterRole -ClusterName HVCL01
Test-CauSetup -ClusterName HVCL01            # the self-updating tests now pass too
```

## 6. Notes

- **Windows updates only.** Server firmware, BIOS and NIC/HBA drivers need the vendor's tools (e.g. Dell). Schedule them separately, one node at a time (drain → update → resume). The CAU Hotfix plugin is out of scope.
- **One host-patching method:** CAU (chosen). Not VMM's WSUS update baselines/remediation for the same hosts.
- **Duration:** ~30–60 min per node (drain + install + reboot + failback), ~2–4 h for HVCL01.
- **SDN phase:** NC and MUX VMs get **anti-affinity** through their VMM availability sets (`AS-SDN-NC`, `AS-SDN-MUX`), so CAU never puts two members of a group on one node. RAS Gateway VMs are **not** clustered: they stay on their host and NC fails over to the standby GW when CAU reboots that host. Patch the host with the standby GW first. See **8.8 §1** and **8.9 §1**.
- Guest VMs are **not** patched by CAU: VMs use `Update-GuestWindows` / their own process.
