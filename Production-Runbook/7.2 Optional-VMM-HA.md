# 7.2 (Optional) Highly available VMM: VMM01 + VMM02 guest cluster

> Based on Microsoft "Plan a highly available VMM deployment" (VMM 2025).
> **Best time:** right after 6.2/6.3, **before 6.5 (NC)** and before customers. Same work, nothing to protect yet.
> If done later: VMM is unavailable ~1–2 h. VMs, NC and tenant traffic keep running.
> ⚠️ Rehearse in a lab first: the "reinstall with existing DB" step has known pitfalls (see §6).

## 0. Microsoft requirements (VMM 2025)

- VMM nodes run **Windows Server 2025**, domain-joined, computer names ≤ 15 chars.
- One VMM instance per failover cluster. The **VMM service name** (clustered role) is ≤ 15 chars.
- ADK (Deployment Tools + WinPE) on **every** node.
- The VMM service account must be a **domain account** (not Local System). DKM **must** be in AD. ✅ Both are already true from 6.2: `svc-vmm` and `CN=VMMDKM`.
- **The library can't be HA on the VMM cluster itself.** It must live on a separate file server (ideally a file server failover cluster; SOFS isn't allowed as library server).
- SQL must not be installed on the VMM cluster (use SQL01 or the 7.1 AG).

| New object | Value |
|---|---|
| VMM02 | 10.10.100.37 |
| Guest cluster `VMMCL01` | 10.10.100.38 (no shared storage, file share witness) |
| VMM clustered service name | **`VMMHA`** – 10.10.100.36. From now on the console connects to `VMMHA.etisalat.local` |
| Library server | `LIB01` – 10.10.100.39 (HA VM on CSV, 1 TB data disk), share `MSSCVMMLibrary` |

## 1. Build VMM02 and LIB01

- **VMM02:** repeat 6.2 §1–2 (VM, IP .37, domain join, svc-vmm + GG-VMM-Admins as local admins, ADK, ODBC, cmd-line utils). **Don't run VMM setup yet.**
- **LIB01:** `New-InfraVM` on CSV + `Add-ClusterVirtualMachineRole`, IP .39, domain join, 1 TB `L:` disk, share:

```powershell
New-Item L:\MSSCVMMLibrary -ItemType Directory
New-SmbShare -Name MSSCVMMLibrary -Path L:\MSSCVMMLibrary -FullAccess "ETISALAT\svc-vmm","ETISALAT\GG-VMM-Admins","ETISALAT\svc-vmm-ras"
```

Anti-affinity on the host cluster (VMM01 and VMM02 on different hosts):

```powershell
foreach ($g in "VMM01","VMM02") {
    $ac = New-Object System.Collections.Specialized.StringCollection; [void]$ac.Add("VMM-HA")
    (Get-ClusterGroup $g).AntiAffinityClassNames = $ac
}
```

## 2. Move the library to LIB01 (while VMM01 still runs standalone)

1. VMM console → **Library → Add Library Server** → `LIB01` (Run As `RA-HostAdmin`, or an account that is local admin on LIB01) → add share `MSSCVMMLibrary`.
2. Copy the content: `robocopy \\VMM01\MSSCVMMLibrary \\LIB01\MSSCVMMLibrary /E /COPY:DAT /R:1 /W:1`
3. Refresh both shares. Re-point templates and NC resources (if NC already exists) to the copies on LIB01.
4. Remove the `VMM01` library share from VMM (**Library → right-click share → Remove**). Don't delete files yet.

## 3. Guest cluster VMMCL01

```powershell
# On VMM01 and VMM02
Install-WindowsFeature Failover-Clustering -IncludeManagementTools -Restart
```

```powershell
# On VMM01
Test-Cluster -Node VMM01, VMM02
New-Cluster -Name "CN=VMMCL01,OU=Clusters,OU=Infrastructure,DC=etisalat,DC=local" -Node VMM01, VMM02 -StaticAddress 10.10.100.38 -NoStorage

Invoke-Command -ComputerName MGMT01 -ScriptBlock {
    New-Item C:\Witness\VMMCL01 -ItemType Directory -Force
    New-SmbShare -Name "Witness-VMMCL01$" -Path C:\Witness\VMMCL01 -FullAccess "ETISALAT\VMMCL01$", "ETISALAT\Domain Admins"
    icacls C:\Witness\VMMCL01 /grant "ETISALAT\VMMCL01$:(OI)(CI)F"
}
Set-ClusterQuorum -Cluster VMMCL01 -FileShareWitness "\\MGMT01\Witness-VMMCL01$"
```

The cluster CNO `VMMCL01$` needs **Create Computer objects** on `OU=Clusters` (to create `VMMHA`). Alternatively, pre-stage `VMMHA` and give `VMMCL01$` full control on it.

## 4. Reinstall VMM01 as the first HA node (keeps all data)

1. **Back up** `VirtualManagerDB` (SSMS full backup). Write down the Update Rollup level.
2. On VMM01: **Programs and Features → Microsoft System Center Virtual Machine Manager → Uninstall → Remove features** → ✔ VMM management server ✔ VMM console → **Database options: Retain database** → Uninstall.
3. Run VMM setup on VMM01 again → **VMM management server** → setup detects the cluster → **"Do you want to make this VMM management server highly available?" → Yes**.
4. Database: server `SQL01` (or the listener `SQLAG-VMM` if 7.1 is done), instance `MSSQLSERVER`, **Existing database → `VirtualManagerDB`**.
5. Service account: **the same** `ETISALAT\svc-vmm`. DKM: **the same** `CN=VMMDKM,DC=etisalat,DC=local`. That's what lets the new install decrypt the existing Run As passwords.
6. Cluster configuration: name **`VMMHA`**, IP **10.10.100.36**.
7. Ports: defaults. Library: **use an existing library share** → `\\LIB01\MSSCVMMLibrary`. Install.
8. Re-apply the same **Update Rollup**.

## 5. Add VMM02 as the second node

On VMM02: VMM setup → VMM management server → setup detects the HA VMM installation on the cluster → confirm, using the same service account / DKM → Install → apply the same Update Rollup.

## 6. After the conversion

- Reinstall the VMM console on MGMT01 if needed, and connect to **`VMMHA.etisalat.local:8100`**.
- **Fabric → Servers:** if hosts show *Access denied / Needs attention*, right-click → **Reassociate** (Run As `RA-HostAdmin`).
- Check Run As accounts, logical networks/switch, and (if deployed) **Network Service NC** = Responding.
- Failover test: `Move-ClusterGroup -Cluster VMMCL01 -Name VMMHA -Node VMM02` → the console reconnects and jobs run → move it back.
- **Known pitfall** (community-reported, not official): if setup fails because the DB "already has HA nodes", the table `tbl_VMM_GlobalSetting` holds stale `HAVMMName` / `HAVMMNodes` values. Only edit after a DB backup, ideally with Microsoft support.
