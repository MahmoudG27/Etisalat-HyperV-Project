## D1. SET switch from day 1, converted by VMM

- Day 1 (1.1 §6): SET switch `LS-Converged` on NIC1+NIC2, host vNICs `Management` (VLAN 100) and `LiveMigration` (VLAN 101). DC/SQL/VMM/MGMT VMs connect to it with VLAN 100.
- After VMM is installed (6.4): VMM **converts** the same switch into the Logical Switch `LS-Converged`.

### What "Convert to Logical Switch" actually does

VMM **doesn't** delete or recreate anything. A Hyper-V switch can carry extra *metadata* (switch extension "features"). Conversion writes two VMM properties into the existing switch:

| Written on | Property | Value |
|---|---|---|
| The switch | VMM switch feature | `LogicalSwitchId` + `LogicalSwitchName` → "this switch belongs to logical switch LS-Converged" |
| The switch's external port (NIC1+NIC2 team) | VMM port feature | `PortProfileSetId` / name → "this uplink uses uplink port profile UPP-Converged" |

Untouched: NIC1/NIC2, the SET team, the host vNICs and their IPs/VLANs, the VMs' connections. That's why Microsoft documents it as **non-disruptive**, and **atomic**: if any step fails, nothing is changed.
(You can see exactly these two properties in the fallback script in 6.4 §6.5. The console button does the same thing.)

From then on, VMM treats the switch as its own:
- It checks **compliance** against the logical switch definition.
- It lets you attach VM networks, port classifications, and later the HNV-PA site.
- In the SDN phase, the Network Controller onboarding turns it into an **SDN switch** (VFP extension enabled).

### Conversion only works if the host switch matches the logical switch

| Setting | Host switch (1.1) | Logical switch (6.4) |
|---|---|---|
| Uplink mode | SET (`-EnableEmbeddedTeaming $true`) | **Embedded Team** |
| Load balancing | `HyperVPort` | **Hyper-V Port** (in uplink port profile) |
| Minimum bandwidth mode | `Weight` | **Weight** |
| SR-IOV | Off | **Off** |
| VLANs in use (100, 101) | on vNICs | covered by the **network sites** in `UPP-Converged` |
| Name | `LS-Converged` | `LS-Converged` (same name: not mandatory for the console, but required by the fallback script and keeps everything readable) |

### Prerequisites and sequence

The conversion needs **(a)** the host already managed by VMM and **(b)** the logical switch already defined. So the order is fixed:

1. Run As accounts (6.3 §1).
2. Host firewall rules for VMM (6.3 §2).
3. Host groups `All Hosts → Etisalat-DC → Cluster1 / Cluster2` (6.3 §3).
4. Add the existing cluster HVCL01 to `Cluster1` (6.3 §4).
5. Logical networks `Management` / `LiveMigration` (sites scoped to `Etisalat-DC`), uplink port profile `UPP-Converged`, logical switch `LS-Converged` (6.4 §1–5).
6. **Convert** per host (host without a DC first), map vNICs to VM networks, confirm **Fully compliant** (6.4 §6).

## D3. One SQL + one VMM to start

- SQL01 and VMM01 are **HA VMs** on HVCL01. A host failure restarts them on another node.
- DKM is stored in AD (6.2), so a second VMM node remains possible.
- Future options, not part of the build: **7.1** SQL Always On (easy, ~15–30 min of VMM downtime), **7.2** VMM HA (reinstall with retained DB, ~1–2 h of VMM downtime).
  In both cases running VMs aren't affected.

## D4. OS / edition matrix and licensing

### Editions (all Windows Server 2025)

| Role | Windows edition | Install option | Image / file |
|---|---|---|---|
| HV01–HV04 (and the 12 hosts later) | **Datacenter** | **Server Core** | ISO install (1.1) |
| DC01, DC02 | Standard | Desktop Experience | `WS2025-STD-DE.vhdx` (1.2) |
| SQL01 | Standard | Desktop Experience | `WS2025-STD-DE.vhdx` |
| VMM01 | Standard | Desktop Experience | `WS2025-STD-DE.vhdx` |
| MGMT01 | Standard | Desktop Experience | `WS2025-STD-DE.vhdx` |
| NC01–NC03, SLB MUX, RAS GW (next phase) | **Datacenter** | Desktop Experience | Generalized Datacenter VHDX (built in the SDN phase) |

| Application | Version |
|---|---|
| SQL Server | **2022 Standard** + latest CU (VMM 2025 supports SQL 2019 / 2022 / 2025) |
| System Center VMM | **2025** + latest Update Rollup |

Why these editions (technical, not a licensing statement):
- **Hosts = Datacenter:** required for SDN on the hosts.
- **NC / MUX / GW = Datacenter:** Network Controller, SLB and multi-tenant RAS Gateway are Datacenter-only features. One generalized VHDX serves all three. Not "Datacenter: Azure Edition".
- **DC / SQL / VMM / MGMT = Standard** guests running on the Datacenter hosts.

### Licensing scope

- **Our scope:** we license only what we own:
  - the physical hosts,
  - DC01/DC02, SQL01, VMM01, MGMT01,
  - NC01–03, the SLB MUX and RAS Gateway VMs,
  - SQL Server and System Center.
- **Customer VMs are the customers' responsibility** (their own Windows/application licensing).
- *Because these hosts serve third-party customers, the licensing program (Volume Licensing vs SPLA) and how customer VMs are licensed on shared hosts must be confirmed by Etisalat's licensing/commercial team with Microsoft before go-live. The technical editions above don't change.*

## D5. iSCSI: two subnets + MPIO (working assumption)

- iSCSI with NIC3/NIC4 + MPIO is the working assumption, most likely what exists today. The storage team confirms it via the questions in 0.2 §7.
- NIC3 → `iSCSI-A` (10.10.110.0/24), NIC4 → `iSCSI-B` (10.10.111.0/24). No gateway, no DNS registration, no NIC team, no vSwitch. Jumbo frames on both NICs and SAN ports.
- **MPIO** (Microsoft DSM or the SAN vendor's DSM) joins the paths into one disk and handles failover.
- If the existing design is **one** iSCSI subnet, it still works. See 5.1 §5 for the single-subnet variant.
- Full explanation in 5.1 §0.

## D6. Tenants on SDN, not VLANs

- Every customer gets its own **VM Network** (HNV/VXLAN over HNV-PA), managed by the Network Controller. Customer VMs keep their current IP ranges, even when two customers use the same range.
- NIC1/NIC2 trunk carries **only** Management, Live Migration and HNV-PA.
- **Future (SDN gateway phase):** one extra VLAN + one /29 per customer that uses the existing FortiGate, as an L3 link between the SDN RAS Gateway and the customer's FortiGate VDOM.
- Open migration items (gateway `.1`, split customers): 0.0 §7.
