## 2. Design decisions taken in this runbook

1. **Tenants run on Hyper-V SDN, not VLANs.** Every customer gets its own VM Network (HNV/VXLAN over the HNV-PA network), managed by the Network Controller. Customer VMs keep their current IP ranges inside their VM Network, even when two customers use the same range. *(Implemented in the next phase.)*
2. **NIC1 + NIC2 → one SET switch named `LS-Converged`** on all 4 hosts (same name everywhere, so VMs can live-migrate).
   Host vNICs: `Management` (VLAN 100) and `LiveMigration` (VLAN 101). Infrastructure VMs (DC/SQL/VMM/MGMT) connect to the same switch on VLAN 100.
   After VMM is installed, VMM **converts** this switch into the Logical Switch `LS-Converged` with no traffic interruption (how it works: 0.1 D1).
3. **Host trunk VLANs are infrastructure only:** Management, Live Migration, HNV-PA. No customer VLANs are trunked.
4. **NIC3 / NIC4 → iSCSI only**, two separate subnets (iSCSI-A, iSCSI-B), no gateway, no team, no vSwitch. MPIO provides redundancy (0.1 D5).
5. **Jumbo frames are required end to end** on host NICs, switch ports, inter-switch links, the HNV-PA L3 hop and SAN ports (0.2 §3). Customer VMs stay at MTU 1500.
6. **DC01 on HV01 local disk, DC02 on HV02 local disk.** They aren't clustered, auto-start with the host, and keep AD alive even if the cluster/SAN is down.
7. **SQL01, VMM01, MGMT01 (jump server)** are **highly available VMs on the CSV**.
8. **One VMM server + one SQL Server 2022** (approved), both HA VMs. DKM is stored in AD from day 1. SQL Always On / VMM HA remain optional (7.1 / 7.2).
9. **Windows Server 2025 Datacenter everywhere, no Standard.**
   - Hosts: Datacenter **Server Core**.
   - All management VMs (DC01/DC02, SQL01, VMM01, MGMT01, later NC/MUX/GW): Datacenter **Desktop Experience**, from **one** golden image `WS2025-DC-DE.vhdx`, activated with **one** AVMA key.
   - The hosts are licensed Datacenter, so guests are covered whatever their edition. One edition means one image to build and patch (0.1 D4).
10. **Network Controller (next phase):** 3-node VM-based NC deployed by VMM from Microsoft's service template. *(Windows Server 2025 can also run NC as a Failover-Cluster role, but that's deployed with SDN Express/WAC, not by VMM.)*
11. **CSV = NTFS 64K**, witness = disk witness on a small LUN.
12. **Copy/paste into VMs**: Enhanced Session Mode on every host + Guest Service Interface on every VM + Desktop Experience guests (1.2).

**Domain:** `etisalat.local` / NetBIOS `ETISALAT`: a placeholder until the company decides (0.1 D2). Must be final **before** step 2.1.

**Physical switch requirements (summary, full request in 0.2):**
- NIC1/NIC2 ports: **trunk**, allowed VLANs **Management, Live Migration, HNV-PA only**. No LACP/port-channel (SET is switch-independent). Portfast/edge.
- NIC3 ports: access iSCSI-A. NIC4 ports: access iSCSI-B. Ideally on two different physical switches.
- **MTU 9216** (or the switch maximum) on all 4 server ports, on the inter-switch links (peer link/ISL), and on every L3 interface/SVI/router hop that carries HNV-PA. **MTU 9000** on the SAN iSCSI ports.
  Reason: VXLAN adds ~50+ bytes. Microsoft's minimum on the PA path is 1674. A single 1500 hop drops large packets while small pings still work.
- HNV-PA must be routed (gateway 10.10.200.1).
- *Future (SDN gateway phase):* one extra VLAN per customer that uses the FortiGate, added to the NIC1/NIC2 trunk.

## 7. Open items before customer migration (discussion only, to decide with Etisalat)

1. **Default gateway = first IP.** In an SDN VM subnet, the default gateway is always the first usable IP (`.1`). It's answered by the distributed router on every host, and VMM reserves it.
   Any customer whose current gateway is **not** `.1`, or that has a VM using `.1`, needs a gateway/IP change during migration. → Check per customer, using the discovery data from 0.2 §5.
2. **Split customers during migration.** A customer that is half on VMware/NSX and half on Hyper-V SDN has **no L2 path** between the two halves.
   Decision needed: migrate each customer as **one wave**, or plan a **temporary L3 path** between the two halves. → To be decided with Etisalat.

## 8. Optional security item: Windows LAPS

The 1.2 answer file sets the **same** local Administrator password in every VM, and the hosts get theirs by hand at install.
Recommended (optional for this build): enable **Windows LAPS** (built into Windows Server 2025, stored in AD) for the local Administrator on the hosts (`OU=Hyper-V Hosts`) and the infrastructure VMs (`OU=Management Servers`):
- extend the AD schema for LAPS (`Update-LapsADSchema`),
- grant the computers permission on those OUs (`Set-LapsADComputerSelfPermission`),
- configure a GPO for the two OUs (back up passwords to AD, rotation period).

Domain controllers keep their DSRM password handling separately.
