# 5.1 iSCSI + MPIO (NIC3 / NIC4)

> Replaces the first half of `5. Failover-Cluster.md`.

## 0. How NIC3 / NIC4 work together

```
            HV0x                                   SAN
   ┌──────────────────┐   iSCSI-A 10.10.110.0/24   ┌───────────────┐
   │ NIC3 10.10.110.x ├──── switch/fabric A ───────┤ CtrlA port A1 │
   │                  │                         ┌──┤ CtrlB port B1 │
   │                  │                         │  │               │
   │ NIC4 10.10.111.x ├──── switch/fabric B ────┼──┤ CtrlA port A2 │
   └──────────────────┘   iSCSI-B 10.10.111.0/24└──┤ CtrlB port B2 │
            │                                      └───────────────┘
        MPIO (DSM): 4 paths → 1 disk
```

- **There's no NIC team on iSCSI.** Teaming iSCSI NICs isn't supported for this; redundancy is done by **MPIO**.
- Each NIC opens its **own iSCSI sessions** to the SAN ports in its subnet: NIC3→A1, NIC3→B1, NIC4→A2, NIC4→B2 = **4 paths**.
- The SAN presents the same LUN (same serial/ID) on all 4 paths. MPIO recognizes that it's one disk, and Windows/the cluster sees **one** disk.
- **Do they work together?** Yes, at the same time:
  - **Round Robin** (or *Round Robin with Subset* / *Least Queue Depth*, per the SAN vendor) spreads I/O over all active paths, so both NICs carry traffic.
  - On **ALUA** arrays (most dual-controller SANs), paths to the controller that owns the LUN are "Active/Optimized" and the others "Active/Unoptimized". MSDSM detects this automatically and prefers the optimized paths.
- **If one fails:**

  | Failure | What MPIO does | Effect on VMs |
  |---|---|---|
  | NIC3, its cable or switch A | Paths 1+2 marked failed, I/O continues on NIC4 paths | None. A few seconds of I/O pause during path failover |
  | SAN controller A | Paths to A1/A2 fail, I/O moves to controller B paths (LUN ownership moves) | None |
  | Path comes back | MPIO re-adds it automatically (path verification) | None |

### Why two subnets is better than one

| | Two subnets (A/B) – recommended | One subnet for both NICs |
|---|---|---|
| Path selection | **Deterministic**: NIC3 can only reach the A-subnet ports, NIC4 only the B ports. The routing table can't send traffic out of the "wrong" NIC | Two NICs with routes to the same subnet. Windows can reply out of the other NIC, or ARP can answer from the wrong NIC. Works only if every session is explicitly bound to its source IP |
| Fault isolation | Two independent fault domains. A loop, broadcast storm or misconfiguration on fabric A doesn't affect fabric B | One L2 domain. A problem there hits both NICs at once |
| Matches SAN design | Most dual-controller SANs (and Microsoft/vendor guides) use A/B fabrics | Some arrays (e.g. group-based designs) require a single subnet. Follow the vendor if so |
| Troubleshooting | "Fabric A is down" is clear | Harder to see which physical path is broken |

Bottom line: both work with MPIO. Two subnets is safer and simpler to operate. **Use whatever the existing SAN design uses** (question #5 in 0.2). Don't create a different design just for the new hosts.

## 1. SAN side (storage team / SAN GUI)

- [ ] iSCSI ports on the SAN: controller A and controller B each have one port on **iSCSI-A (10.10.110.0/24)** and one on **iSCSI-B (10.10.111.0/24)**.
      Example: A1 = 10.10.110.201, B1 = 10.10.110.202, A2 = 10.10.111.201, B2 = 10.10.111.202.
- [ ] MTU 9000 on the SAN ports.
- [ ] Host group `HVCL01` with the **4 initiator IQNs** (collected below).
- [ ] LUNs mapped to that host group (same LUN ID on all hosts):
  - LUN 0 – `Witness` – 5 GB
  - LUN 1 – `CSV01` – infrastructure VMs (DC are local; SQL/VMM/MGMT/NC/library ≈ 2–3 TB with growth). Add more CSV LUNs for tenants later.
- [ ] Vendor: check whether the SAN needs its own DSM/MPIO package or a specific load-balance policy (Dell / HPE / NetApp / Huawei…). If it does, install it **instead of** the Microsoft DSM settings below.

Get each host's IQN:

```powershell
Invoke-Command -ComputerName HV01,HV02,HV03,HV04 -ScriptBlock { "$env:COMPUTERNAME  $((Get-InitiatorPort | Where-Object ConnectionType -eq 'iSCSI').NodeAddress)" }
```

## 2. On every host: iSCSI service + MPIO claim

```powershell
Set-Service -Name MSiSCSI -StartupType Automatic
Start-Service -Name MSiSCSI

Enable-MSDSMAutomaticClaim -BusType iSCSI
Set-MSDSMGlobalDefaultLoadBalancePolicy -Policy RR     # Round Robin; use the vendor's recommendation if different
Restart-Computer
```

## 3. On every host: two sessions per controller port (one per NIC)

```powershell
$Id = 11                              # HV01=11 ... HV04=14
$InitA = "10.10.110.$Id"              # NIC3
$InitB = "10.10.111.$Id"              # NIC4
$PortalsA = "10.10.110.201","10.10.110.202"
$PortalsB = "10.10.111.201","10.10.111.202"

# Jumbo test first (8972 + 28 header = 9000)
$PortalsA | ForEach-Object { ping $_ -S $InitA -f -l 8972 -n 2 }
$PortalsB | ForEach-Object { ping $_ -S $InitB -f -l 8972 -n 2 }

# Register portals, bound to the right source NIC
$PortalsA | ForEach-Object { New-IscsiTargetPortal -TargetPortalAddress $_ -InitiatorPortalAddress $InitA }
$PortalsB | ForEach-Object { New-IscsiTargetPortal -TargetPortalAddress $_ -InitiatorPortalAddress $InitB }

Get-IscsiTarget | Format-Table NodeAddress, IsConnected
```

Copy the exact `NodeAddress` (it looks like `iqn.YYYY-MM.com.vendor:...`), then connect **every portal/initiator pair**:

```powershell
$TargetIqn = "iqn.2002-03.com.vendor:storage.example-target"     # <-- paste the real NodeAddress
# Some SANs expose one target IQN per controller/LUN group. If Get-IscsiTarget lists more than one, repeat for each.

foreach ($p in $PortalsA) { Connect-IscsiTarget -NodeAddress $TargetIqn -TargetPortalAddress $p -InitiatorPortalAddress $InitA -IsPersistent $true -IsMultipathEnabled $true }
foreach ($p in $PortalsB) { Connect-IscsiTarget -NodeAddress $TargetIqn -TargetPortalAddress $p -InitiatorPortalAddress $InitB -IsPersistent $true -IsMultipathEnabled $true }
```

## 4. Verify paths (every host)

```powershell
Get-IscsiSession | Format-Table TargetNodeAddress, InitiatorPortalAddress, IsConnected, IsPersistent
Get-IscsiConnection | Format-Table InitiatorAddress, TargetAddress
mpclaim -s -d                                   # list MPIO disks
mpclaim -s -d 0                                 # paths of MPIO disk 0 (expect 4 paths: 2 NICs x 2 controllers)
Get-Disk | Where-Object BusType -eq iSCSI | Format-Table Number, FriendlyName, Size, OperationalStatus, IsOffline
```

**Each LUN must appear exactly ONCE in `Get-Disk`.** If a LUN shows twice, MPIO isn't claiming it: check the vendor DSM and the reboot from step 2.

> ⚠️ Do **not** initialize, online, or format disks on HV02/HV03/HV04. That happens once, on HV01, in 5.2.

## 5. Variant: the existing SAN uses ONE iSCSI subnet

Only if the storage/network team confirms a single iSCSI subnet (for example 10.10.110.0/24 for everything):

```powershell
$Id = 11
$InitA = "10.10.110.$Id"           # NIC3
$InitB = "10.10.110.$($Id + 100)"  # NIC4, same subnet, e.g. .111 for HV01
$Portals = "10.10.110.201","10.10.110.202"   # all SAN iSCSI ports in that subnet

# In 1.1 §7, give NIC4 $InitB in the SAME subnet (no gateway, no DNS registration).

# Every session MUST name its InitiatorPortalAddress. That's what forces traffic out of the right NIC
foreach ($p in $Portals) {
    New-IscsiTargetPortal -TargetPortalAddress $p -InitiatorPortalAddress $InitA -ErrorAction SilentlyContinue
    Connect-IscsiTarget -NodeAddress $TargetIqn -TargetPortalAddress $p -InitiatorPortalAddress $InitA -IsPersistent $true -IsMultipathEnabled $true
    Connect-IscsiTarget -NodeAddress $TargetIqn -TargetPortalAddress $p -InitiatorPortalAddress $InitB -IsPersistent $true -IsMultipathEnabled $true
}
Get-IscsiSession | Format-Table InitiatorPortalAddress, TargetNodeAddress, IsConnected
```

Expect sessions from **both** initiator IPs. If all sessions show only `$InitA`, the binding didn't work: check the `-InitiatorPortalAddress` values.
