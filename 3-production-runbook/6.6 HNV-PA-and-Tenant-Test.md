# 6.6 HNV Provider network + first tenant virtual network (proves SDN works)

> Microsoft's validation step after NC deployment. When this passes, VMM + NC + SDN networking is working end to end.

## 1. Logical network HNV-PA (managed by NC)

**Fabric → Networking → Logical Networks → Create Logical Network**

| Page | Value |
|---|---|
| Name | `HNV-PA` |
| Settings | **Connected network** · ✔ **Allow new VM networks created on this logical network to use network virtualization** · ✔ **Managed by Microsoft Network Controller** · ✘ create VM network with same name |
| Network Site | `HNV-PA_0` · Host group **SDN** · VLAN **200** · 10.10.200.0/24 |

IP pool (required even if DHCP exists). Right-click `HNV-PA` → **Create IP Pool**:

| Field | Value |
|---|---|
| Name | `IPP-HNV-PA` |
| Range | 10.10.200.10 – 10.10.200.250 (don't use the first address) |
| Gateway | 10.10.200.1 |
| DNS | 10.10.100.21, 10.10.100.22 |

## 2. Add HNV-PA to the uplink port profile

**Fabric → Networking → Port Profiles → `UPP-Converged` → Properties → Network configuration** → ✔ `HNV-PA_0` → OK.

VMM pushes the PA network to all hosts (Microsoft: "Ensure that you select the network site corresponding to the HNV provider logical network in the uplink port profile").
Check host compliance in **Logical Switches → Hosts**. Remediate if needed.

Verify on the hosts (each host gets PA addresses from the pool, usually one per SET member NIC):

```powershell
Invoke-Command -ComputerName HV01,HV02,HV03,HV04 -ScriptBlock { Get-ProviderAddress } | Format-Table PSComputerName, ProviderAddress, VlanID, MacAddress
```

## 3. Tenant VM network (HNV / VXLAN)

**VMs and Services → VM Networks → Create VM Network**

| Page | Value |
|---|---|
| Name | `VMN-Tenant-Test` |
| Logical network | `HNV-PA` |
| Isolation | **Isolate using Hyper-V Network Virtualization** (the only valid option on an NC-managed network) |
| IP protocol | IPv4 |
| VM subnet | `Subnet1` – `192.168.50.0/24` |
| Connectivity | none (no gateway yet) |

Right-click it → **Create IP Pool** → `IPP-Tenant-Test` · 192.168.50.10 – 192.168.50.100 · gateway 192.168.50.1 (the distributed router answers on .1) · DNS optional.

> Customer address space (192.168.50.0/24) is fully isolated. Every customer can reuse the same ranges. This is what replaces per-tenant VLANs from VMware.

## 4. Two test VMs on two different hosts

Create a VM template once (**Library → Templates → Create VM Template**):
- Source `VHDs\WS2025-DC-NC.vhdx` (already generalized) · Gen 2 · 2 vCPU / 4 GB
- Network adapter → VM network `VMN-Tenant-Test`, **Static IPv4** from pool
- Guest OS: admin password, time zone; **workgroup** (no domain: this network can't reach the DCs).
Name it `TPL-TestVM`.

Deploy `TEST01` on **HV01** and `TEST02` on **HV03** (Create Virtual Machine → from template → placement: choose host manually).

Inside each VM (VMM console → **Connect via Console**; copy/paste works through enhanced session):

```powershell
New-NetFirewallRule -DisplayName "Allow ICMPv4-In" -Protocol ICMPv4
ipconfig
ping 192.168.50.11      # the other VM's IP
```

✅ **Ping between TEST01 and TEST02 works** = NC is programming VFP policies on both hosts and the VXLAN encapsulation over VLAN 200 is fine.

Troubleshooting if ping fails:
- `Get-ProviderAddress` on both hosts shows PAs? Can the PAs ping each other with a big packet? On a host: `ping <other host PA> -S <this PA>` (uses VLAN 200 + MTU).
- Jumbo / MTU on VLAN 200 on the physical switches (≥ 1674).
- Look at `Get-PACAMapping` on the hosts. The test VMs' CA→PA mappings must be present.
- Debug tooling: `Install-Module SdnDiagnostics` on MGMT01, then `Debug-SdnFabricInfrastructure -NetworkController NC01`.

Delete TEST01/TEST02 when done, or keep them powered off for testing after each patch cycle.
